## 三个 Agent 与图的职责

| 角色 | 职责 | 权限边界 |
| --- | --- | --- |
| Design Agent | 设计场景、依赖、检查点和业务验收条件；发现缺失需求并澄清 | 不能把页面表现当作正确规则，不能编造来源 |
| Execution Agent | 根据当前观察规划动作，通过受控工具完成操作；根据诊断提出修复动作 | 不能修改冻结的验收条件、关键输入、资源权限或预算 |
| Diagnosis Agent | 根据证据分析失败，保留未知和不确定性，给出归因及调查建议 | 不能替代程序断言或把缺少证据的判断当作产品缺陷 |

同一模型可以服务三个 Agent；角色通过独立提示词、上下文和结构化协议区分。修复规划归 Execution Agent，修复批准归确定性程序校验。模型服务备用不属于新增 Agent。

主图预计 7 个入口节点，其中一个入口为执行子图：观察网站、设计用例、需求澄清、执行子图、导出脚本、独立重跑、结果分析与报告。执行子图预计 10 个节点：选择检查点、观察页面、规划动作、执行单步动作、等待人工资源、验收检查点、诊断失败、规划修复、校验修复、完成检查点。展开约 16 个工作节点，不重复计算子图入口，也不计 START/END。节点数量是设计估计，不能作为功能完成证明。

- LangGraph 拥有场景依赖推进、检查点与动作回边、等待分支、诊断修复分支、预算停止和结果汇总路径。节点一次推进一个明确步骤，不能把旧协调器全部循环改名塞入单个节点。
- 图状态保存逻辑位置、动作队列、待资源请求的公开引用、预算与修复记录、原始失败、验收结果及证据引用；不能把这些进度再藏在第二套运行循环里。
- 普通运行服务负责浏览器生命周期、单步定位与动作、结构校验、脱敏、文件与报告、资源输入及 IPC。截图等细节不单独包装成模型 Agent。
- 浏览器对象和敏感值不进入可持久化图状态。运行期服务维护真实对象，图只保存公开句柄引用及逻辑状态。
- 同一场景保持一个浏览器上下文，同一业务链不重复登录、索取验证码；独立场景隔离。
- 进程存活时可继续等待流程；重启从安全起点重建浏览器，不恢复旧句柄、OTP 或未知副作用。不承诺跨进程恢复旧页面，也不承诺任意崩溃下的恰好一次外部提交。
- 单步动作由受控 Playwright 工具实际执行，普通动作无需每步重调模型。遇到已经尝试提交的未知结果，保留证据并停止自动重复。
- 脚本独立重跑继续无模型/API key/原项目依赖；导出依赖闭包必须随执行实现更新，避免永久保留两套业务执行器。
