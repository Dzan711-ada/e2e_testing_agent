# 受约束修复

使用原有解释器运行 `main.py run --shop --repair --query "测试注册、登录和购物车，数量为1且刷新保留；验证错误密码和未登录访问"`。`--repair` 只对当前商城 Agent 流程启用。普通 `replay` 使用已经生成的动作，不调用模型；`diagnose` 仍只产生诊断。

诊断角色先基于当次事实判断，再提出可执行 RepairPlan。程序核对原规则与完整数据摘要、原操作与关键输入、资源身份、范围、重启检查点、已存在的证据及次数。当前只支持同一业务控件的定位调整，或一次受原操作时限约束的等待；不执行模型 Python，不提高超时，不删除或修改验收条件。

同一故障最多2次修复，另受场景、全套件动作、主动时间和模型调用上限约束；无剩余预算即停止。修复不能跳回注册或登录，更不能重复索取验证码。页面已提交而响应不确定时停止并留证，不盲目重复发码或加购。断言失败不会被当作定位调整重试，从而保留认证／数量／会话异常。

每次尝试单独保存原动作、错误、掩码截图、诊断、计划、程序决定和实际结果。成功后仍执行原检查，导出修复后的新动作，保留原计划与错误事件；结果标记 repaired、次数和不一致性。首次失败与独立重跑成功分开记录，不覆盖旧结果或宣布稳定通过。

该能力针对已声明的本地商城控件语义。其他站点、无法证明未发生副作用、未知控件含义或缺少规则来源时停止调查，不保证可自动恢复。

完整门禁：`scripts/verify_stage.py --stage 6`。固定输出验证只证明程序策略；真实模型另验证可恢复的定位问题和必须停止的产品问题。G6全部通过前，不进入阶段7。
