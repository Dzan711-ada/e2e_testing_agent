## 1. 交接目标与已经确认的需求

在当前 Python 项目上扩展，不重新迁移 notebook，不另建一套平行实现。保留 PyCharm 运行、独立解释器、Playwright 浏览器执行、脚本导出和独立重跑能力。

目标是：用户以自然语言提出网站测试目标；系统观察网站、通过交流补齐必要规则和资源，设计多个用例并执行；发生失败时基于证据诊断，并对适合恢复的操作错误进行受约束修复。

用户已确认：

1. 首版以自建可控示例网站为主要开发和评测环境，同时兼容选定的公开练习站，不把“任意网站均可成功”作为承诺。
2. 使用 PyCharm 控制台交流，直接回车发送；不引入 `/send`，首版不开发聊天网页界面。
3. 用户同时要求测试登录和购物车时，Agent 应规划依赖顺序：先完成并检查登录，再沿用这次登录成功的浏览器会话测试购物车。
4. 同一业务链内不要为每个功能重新登录、重新索取验证码；登录是被测功能，也是后续操作的前置条件。
5. 多用例数量由系统根据范围和规则规划；用户没说清且影响正确性的业务规则、成功条件和测试资源，通过询问获取。
6. 需要手机号、当次验证码等资源时，允许暂停并询问用户，获得资源后继续；生成脚本必须能够表达和重现这些资源请求。
7. 失败诊断需要区分疑似网站缺陷与 Agent 操作／代码问题；适合自动修复的情况，由 Agent 提出重试计划，程序检查约束后执行。
8. 引入职责明确的多 Agent，继续采用 LangGraph；不以更换 CrewAI 或增加 Agent 数量为开发目标。
9. 每阶段必须先完成测试、处理失败，再进入下一阶段；不得一次性完成全部功能后才补验证。

## 3. 范围、架构与关键约定

### 3.1 三个 Agent 与一个程序协调器

| 组件 | 职责 | 不应拥有的权限 |
| --- | --- | --- |
| 需求与测试设计 Agent | 观察页面入口；识别规则、缺失信息和资源；集中澄清；设计业务链和独立用例；定义验收条件 | 从页面实际表现自行推导正确业务规则；把未确认假设当事实 |
| 执行 Agent | 根据当前页面和目标规划下一步操作；产生结构化动作；调用受控浏览器工具；记录实际结果 | 擅自删除检查、修改业务预期或改变关键输入来获得通过 |
| 审查与诊断 Agent | 核对需求—动作—检查—证据关系；分析失败；提出调查和修复计划；检查修复是否偏离原目标 | 凭异常名称直接宣布产品 Bug；将证据不足强制归为网站或 Agent 错误 |
| 确定性协调器 | 调度场景和角色；管理依赖、会话、人工等待、资源、预算；校验计划；确定运行状态 | 把模型的“成功”声明直接作为测试结果 |

三个 Agent 可以使用同一个底层模型，但提示词、工具权限、输入和结构化输出分开。模型供应商降级是服务备用机制，不是多 Agent 协作。

浏览器生命周期、资源注入、代码编译、重跑、结果汇总由普通程序实现。不要把截图保存等确定性操作再包装成无必要的 LLM Agent。

### 3.2 测试套件、业务链与检查点

- **测试套件**：一次用户请求下的所有测试范围和场景。
- **业务链／场景**：有起点和终点、可完整重跑的一条流程。例：注册新账号 → 登录 → 添加购物车。
- **检查点**：链中某个业务结果的验收。例：注册成功、登录成功、购物车出现指定商品且数量正确。
- **独立用例**：具有独立前置状态的其他场景。例：错误密码登录、必填字段缺失、未登录访问购物车。

一条业务链导出一个 Pytest 用例，链内检查点单独统计和留证；独立场景分别导出其他 Pytest 用例。不要为了把登录和加购拆成两个 Pytest 函数而破坏共享会话或引入测试执行顺序依赖。

用户请求登录和购物车时，计划至少包含登录验收与购物车验收。若系统漏掉其中一项，即使执行成功也属于需求未落实。

### 3.3 登录态：用户要求的准确实现

同一轮、同一条业务链：

```text
准备账号／向用户获取资源
  → 登录操作
  → 检查登录确实成功
  → 保留当前 BrowserContext、页面与业务变量
  → 进入商品页并加购
  → 检查购物车商品、数量等预期
```

- 每轮执行只完成一次需要的登录；加购步骤不重新索取验证码。
- 页面跳转或创建同一上下文中的新页面，不应丢失当前会话。
- 登录失败后依赖登录的检查点记为 `blocked`，原因关联登录检查；不能记为购物车缺陷。
- 错误密码、未登录访问等冲突场景使用独立上下文，避免污染主链。
- 登录态意外丢失时先留证和诊断，不能悄悄重新登录掩盖会话问题。
- 浏览器隔离不能替代后台数据隔离；账号、购物车和商品数据需要单独管理。

整条业务链独立重跑是新一轮：创建新的执行上下文，从规定起点重新完成登录检查，再继续购物车。验证码必须重新获取。首次生成执行和独立重跑各算一轮，报告明确展示，不声称整个任务永远只登录一次。

单独运行购物车时，可以显式提供已经验证的登录前置条件，但不能据此声称这次也验证了登录功能。跨运行持久保存真实登录态不是首版主路径；首版优先实现同链当前会话复用。

### 3.4 验收条件与来源

每项业务预期应记录来源：用户直接说明、澄清答复、明确的需求／网站约定。页面观察只是“当前看到了什么”，不能单独充当业务正确性的依据。

不明确且影响测试正确性的规则进入待澄清状态，不能编造。用户已给出的信息不重复询问；多个缺口尽量合并成简短问题。与执行无关的细枝末节采用明确记录的默认策略，不强迫用户设计每个按钮操作。

规则和验收条件保留版本及摘要指纹。修复可以调整定位与执行方式，但不能降低预期、删除必须检查的条目。对规则的修改必须回到需求澄清，并形成新版本。

### 3.5 动作层与脚本导出

新增主执行路径使用经过校验的结构化动作，而不是仅靠提示词限制任意 Python：

- 动作示例：观察页面、填写、点击、选择、勾选、导航、等待明确条件、检查状态／文本／URL、请求资源。
- 明确动作目标、业务意图、前置条件、数据或资源引用、期望后置状态。
- 定位从实际观察到的候选元素生成；执行前检查匹配和可操作性，避免无条件取第一个匹配。
- URL 范围、允许的工具、动作数、执行时间和模型调用由协调器检查。
- 确定性执行器和编译器把动作转成 Playwright Python。结构化约束降低错误和越界机会，但不保证模型选择的目标语义绝对正确。
- 首版支持常见表单和导航交互；不支持的能力明确报告，不能通过无限制代码后门绕过动作约束。

保留旧流程适配器，分阶段迁移。导出仍是可在 PyCharm 使用的普通 Python 测试工程，可附带资源和检查点支持模块，不承诺每个场景都能压缩成一个无依赖文件。

普通重跑无需调用模型；主动启用诊断／修复时才调用对应 Agent，并产生新版本，不能偷偷修改历史脚本。

只有完整生成了场景所需操作和检查，才标记为完整可执行测试。提前中断时保留部分动作、未完成事项和诊断；可以导出范围明确的失败复现，但不能冒充已完成整个业务链。

### 3.6 结果、归因与稳定性分开

建议独立字段：

| 维度 | 建议取值／内容 |
| --- | --- |
| 执行状态 | pending、running、waiting_user、passed、failed、error、blocked、cancelled |
| 归因 | suspected_product、agent_execution、environment、requirements、unknown |
| 稳定性 | consistent、inconsistent、unverified |
| 参与标志 | 是否人工辅助、是否经过修复、修复次数 |
| 证据 | 预期与实际结果、操作记录、页面与 URL、断言、脱敏日志／截图、相关错误 |

`failed` 不等于已确认产品 Bug；`unknown` 是有效结论。不能凭超时或 AssertionError 分类。没有证据的模型置信度不能替代验证。

错误密码被拒绝，是负向登录用例的通过。已知会失败的注入场景必须由测试框架断言其正确失败；这不意味着用户测试报告要把真实失败改为通过。

零用例、必需用例未执行、预期外跳过、缺少 JUnit、错误用例集合、非零异常退出，都不能报告套件通过。阶段 2 后不再固定“恰好一个用例”，而是匹配本轮计划的场景身份与集合。

## 4. 人工资源设计

### 4.1 资源请求

资源请求至少描述：类型、用途、所属场景／步骤、是否敏感、是否当次有效、是否可复用、等待期限、校验方式和取消方式。

手机号与验证码分开。验证码绑定当前手机号、当前登录挑战和当前运行，过期后不能继续使用。格式合法不代表验证码有效，最终仍依据网站结果检查。

模型和脚本使用资源引用；明文由资源管理器直接交给浏览器填写。首版资源类型覆盖账号／密码、手机号、短信验证码；其他资源以后扩展。

### 4.2 运行与重跑

```text
执行器识别需要手机号 → 主控制台询问 → 填写手机号
  → 单独执行并记录发码动作
  → 进入等待验证码状态
  → 主控制台获取当次验证码
  → 填写并提交 → 验证登录 → 同会话继续加购
```

- 不允许模型在生成片段里直接调用 `input()`。
- 当前 Pytest 子进程输出被重定向到日志；重跑资源请求必须通过本机 IPC／资源代理返回主控制台，不能只在子进程里打印提示后卡住。
- 定义统一 `ResourceProvider` 接口：脚本化测试提供者、控制台提供者，以及重跑桥接提供者；避免多个进程争抢标准输入。
- 人工等待不计入一般浏览器操作超时，但有独立等待期限；模型和工具挂起仍受执行超时限制。
- 无交互输入渠道时，缺少人工资源应得到明确的 blocked 结果，不无限等待，不按通过处理。
- 发码与等待放在不同节点，保存动作记录，避免暂停恢复导致重复发码。外站无法证明动作是否完成时，先观察或请求澄清，不直接重复提交。
- 首版支持进程存活期间暂停与继续。重启后的逻辑状态可恢复，但旧浏览器句柄不能持久化；从场景安全起点重新开始并重新获取必要资源。

### 4.3 资源与证据处理

- 实际手机号、密码、验证码、认证令牌不写入模型上下文、导出脚本或普通报告；状态持久层保存资源引用，明文默认仅保留必要生命周期。
- 页面观察、异常、URL 和日志按资源注册表脱敏。不能只脱敏 Markdown，却把值留在 JSON、DOM、截图或 trace 中。
- 涉及真实敏感资源的场景默认不保存可能带认证内容的原始 DOM／网络载荷／完整 trace，使用受限脱敏事件和掩码截图；公开虚构示例可保留完整调试轨迹。
- 认证状态如确需落盘，应本地隔离、排除版本控制并声明生命周期；首版不默认保存跨运行真实登录态。
- 图形／滑块验证不是短信输入。首版如遇此类挑战，可提示用户在有界面浏览器手动完成并重新观察，或明确标记暂不支持；不承诺自动绕过。

## 5. 可控示例与评测设计

在原注册 demo 之外新增小型测试商城，保留旧 demo 用于回归。建议沿用 Flask，后台数据可用 SQLite，保持普通 Python 项目规模。

最少具备：注册、账号登录、模拟短信登录、商品列表、购物车、退出登录，以及测试模式的数据准备和重置能力。模拟短信不调用真实短信服务；人工输入通过本地测试通道提供，自动测试使用脚本化资源提供者。

每轮数据具有独立命名空间，避免首次注册后独立重跑因账号重复而失败。数据生成规则在计划中声明并冻结，不作为失败后偷偷更换输入的修复手段。

可切换的已知变化至少覆盖：

| 类型 | 场景 | 预期行为 |
| --- | --- | --- |
| 正常 | 登录后加购 | 每轮只登录一次，所有业务检查通过 |
| 正常负向 | 错误密码被拒绝 | 负向用例通过 |
| 操作问题 | 提供一个过时定位，但页面目标仍存在 | 识别并修正定位，业务预期不变 |
| 歧义 | 页面有多个同名按钮 | 缩小定位范围，不能随意点第一个 |
| 异步 | 页面或响应延迟 | 在已规定预算内等待；不无限提高超时 |
| 产品问题 | 正确账号被错误拒绝 | 保留疑似产品失败，不换账号获得通过 |
| 产品问题 | 错误密码也能登录 | 检出认证规则违反 |
| 产品问题 | 加购后数量错误或刷新丢失 | 检出购物车缺陷 |
| 会话问题 | 登录后异常丢失会话 | 留证并诊断，不自动重新登录掩盖问题 |
| 资源 | 验证码缺失／过期／取消 | 正确等待、重新请求或结束，依赖项阻塞 |
| 环境 | 连接失败、服务异常 | 提供证据，允许环境或未知归因 |
| 不稳定 | 首次失败、重跑成功 | 保留两次结果，标记不一致 |

故障配置由测试框架持有，不把故障名称或正确分类答案提供给 Agent。诊断评测使用固定证据样例与真实浏览器事件两类输入；保留未参与调试的场景评估泛化。

## 6. 分阶段开发与强制测试门槛

### 通用规则：所有阶段均执行

1. 一次只实施当前阶段；不要先把后续模块全部写完再声称逐阶段验证。
2. 阶段开始前查看上一阶段验证记录与当前工作树；保留用户变更。阶段结束运行完整离线回归和该阶段规定的集成测试。
3. 必需测试失败、超时、未运行或被跳过，均未满足阶段门槛；先修复，不能进入下一阶段，也不能自动把该项改为可选。
4. 公网可用性测试可以预先声明为可选；本地可控集成测试不可因为公网不可用而取消。
5. 真实模型专项测试与离线测试分开；需要验证模型能力的阶段不能仅用假模型通过就宣告完成。调用只使用当前会话授权范围内的数据和服务。
6. 正常场景必须通过；预期失败／阻塞场景必须被正确识别。测试驱动程序对这些预期进行断言，验证命令整体应成功。
7. 不通过弱化断言、删除回归、隐蔽跳过、只改状态字段或伪造日志满足门槛。因接口合理变化而更新旧测试时，保留原测试要保护的行为并说明理由。
8. 每阶段记录修改、命令、退出码、测试数量、预期／实际结果、产物位置和遗留问题。验证必须对应最终代码，验证后有相关修改就重跑受影响测试。
9. 遇到外部阻塞时如实报告当前阶段未完成及原因，可以继续当前阶段不受影响的工作，但不开始下一阶段实现。

建议新增 `scripts/verify_stage.py --stage N` 作为统一验证入口；它是待开发脚本，不能在创建前假装已存在。报告保存至 `runtime/development/stage-N/运行标识/`，进度记录写入 `docs/DEVELOPMENT_PROGRESS.md`。

### 阶段 4：人工资源、暂停恢复与交互重跑

**开发内容**

- 实现统一 ResourceProvider、主控制台问答、敏感输入、请求身份和生命周期。

**必需验证**

- 脚本化提供者稳定验证完整手机号 → 发码 → 验证码 → 登录 → 加购流程；每轮发码、登录各一次。

- 程序中断或重启后，不错误使用过期资源或把旧登录检查当作新会话已登录。

### 阶段 5：证据收集与诊断 Agent，暂不自动修复

**开发内容**

- 建立预期／实际／代码／页面／URL／错误／脱敏网络元信息的证据关联。
- 接入诊断 Agent，输出结构化归因、证据引用、反证、不确定项和建议调查／修复计划。
- 独立审查需求覆盖，不能只信执行 Agent 的自然语言总结。
- 本阶段只诊断和提出计划，不自动执行修复，先验证判断质量。

**必需验证**

- 固定证据集覆盖操作错误、疑似产品问题、环境、规则冲突和未知；分类必须引用存在的证据。

- 页面已成功但断言定位错误，不直接报告产品 Bug；正确执行后业务结果错误，不直接改为定位问题。
- 未知证据返回 unknown；缺少预期来源时进入澄清而不是编造判据。
- 真实模型完成至少一个已知操作问题、一个已知产品问题和一个证据不足场景的诊断；产物不泄漏故障开关答案。
- 预先指定的关键场景均判断正确；扩展集记录分类表现，不用事后修改标签美化结果。
- 全量回归与浏览器测试通过。

**门槛 G5**：诊断基于证据、有不确定性出口；不能仅凭报告写得合理就验收。

**必需验证**

- 首次失败与重跑成功仍保留不一致；修复后通过带 repaired 标志，不覆盖原失败记录。
- 真实模型验证至少一个可修复故障和一个应停止修复的产品故障。
- 全量回归、资源重跑、正常／故意失败链路通过。

**门槛 G6**：既证明能恢复部分操作错误，也证明不会通过修改测试目标掩盖已知产品缺陷。

## 8. 阶段进度和证据格式

`docs/DEVELOPMENT_PROGRESS.md` 每阶段至少包含：

```text
阶段：N / 名称
状态：未开始 / 开发中 / 验证中 / 已通过 / 外部阻塞
输入基线：提交或源文件摘要、依赖锁版本
已实现：对应方案条目
测试：命令、时间、退出码、数量、结果文件
场景：正常／预期失败／资源等待／重跑的实际结果
模型调用：是否真实调用、服务与模型、数据范围（不含密钥）
遗留问题：没有则明确写无；有则说明是否阻止阶段通过
门槛：G_N 是否满足及证据链接
下一阶段：只有当前门槛满足才开始
```

阶段机器记录至少保存预期和实际场景身份、测试命令退出码、通过／失败／阻塞统计、代码版本、关键产物路径。不要把敏感输入存入验证记录。

建议评测指标：

- 关键需求的已实现检查比例，人工抽查其语义；不能把数量覆盖当成完整正确性证明。
- 正常场景误报率、已知产品缺陷检出率、操作错误率。
- 诊断分类表现和 unknown 比例，避免靠全部输出 unknown 获得表面低误判。
- 可修复问题的正确恢复率，以及修复导致的产品缺陷漏检。
- 首次／独立重跑一致性、人工交互次数、模型调用／token、耗时。

任何百分比都必须同时给出样本数量、场景范围和运行条件。不能提前写入虚构改进数字。
